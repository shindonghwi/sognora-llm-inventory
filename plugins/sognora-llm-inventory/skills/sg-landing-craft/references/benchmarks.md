# 벤치마크 프로토콜 — "잘 만든 것"의 기준은 룰이 아니라 실측에서

> 제작 착수 전 필수 절차. 추상 룰만으로 방향을 정하면 "룰은 지켰는데 허접한" 결과가 나온다.
> 대상 단위는 랜딩만이 아니다 — **페이지(마케팅·앱 화면·대시보드) / 섹션 / 컴포넌트** 각각에 맞는 벤치마크를 고른다.

## 0. 라이브러리 우선 — 매 실행마다 분석하지 않는다

**`references/library/`가 이 스킬의 축적 자산이다.** 한 번 분석한 레퍼런스는 분석 문서(구조·자산 운용·인터랙션·수치)로 저장되고, 이후 모든 실행은 문서를 **읽기만** 한다(브라우저 비용 0).

1. `references/library/INDEX.md`에서 대상과 같은 장르·단위의 문서 2~3개를 고른다 — 있으면 §1~2를 전부 건너뛴다.
2. 라이브러리에 맞는 장르가 없거나 사용자가 특정 URL을 줬을 때만 §1~2(스캔+프로브)를 1회 수행하고, **분석 문서를 라이브러리에 저장 + INDEX에 한 줄 등록**한다. 실행할수록 라이브러리가 두꺼워지는 구조다.
3. 프로젝트별 `_landing/bench/`에는 **자기 페이지 측정만** 남긴다. 레퍼런스 지식은 전부 라이브러리로.
4. 라이브러리 문서에 "인터랙션: 미채움" 표시가 있으면 여유 있을 때 probe 1회로 채운다 — 실행을 막지는 않는다.

## 1. 레퍼런스 선정 (대상 단위별, 2~3개)

사용자가 준 레퍼런스가 최우선. 없으면 대상 단위에 맞는 소스에서 같은 장르로 고른다:

**마케팅·랜딩 페이지**
- Land-book (land-book.com) — 최대 큐레이션, 섹션 단위 필터(가격표·비교표만 모아보기 가능)
- Godly (godly.website) — 동시대 하이엔드
- Saaspo · SaaSFrame — SaaS 랜딩 전문
- Lapa Ninja (lapa.ninja) · Awwwards (수상작 — 장식 과다 주의, 프로덕트엔 선별 적용)

**프로덕트 UI — 앱 화면·대시보드·플로우**
- Mobbin (mobbin.com) — 실제 프로덕션 앱의 온보딩·설정·결제까지 전체 플로우, 화면 유형별 태깅
- Refero (refero.design) — 실서비스 웹앱 화면
- Page Flows — 실사용 플로우 녹화 (인터랙션 벤치마크)

**컴포넌트·디자인 시스템**
- The Component Gallery (component.gallery) — 실계 디자인 시스템들의 동종 컴포넌트 비교(버튼·테이블·모달을 시스템별로 나란히)
- 1군 디자인 시스템 문서 직접 참조: Polaris(Shopify) · Carbon(IBM) · Primer(GitHub) · Atlassian — 크기·패딩·상태·토큰의 근거 있는 스펙

**한글 기준점**: toss.im 및 토스 계열 제품 — 한글 타이포·밀도·컴포넌트의 국내 최상급 실례

## 2. 실측

**페이지 단위** — 레퍼런스당 1회:
```
node scripts/detect.mjs --url <레퍼런스> --out _landing/bench/<이름> --viewports 1440x900
```
갭 지표 5개:
| 지표 | 계산 |
|---|---|
| 폰트 단수 | `page.fontSizes.length` |
| 디스플레이 배율 | max(fontSizes) ÷ 본문 중앙값(12~20px 범위) |
| 밀도 중앙값 | 섹션별 `contentArea/(width×height)` 중앙값 |
| 자산 다양성 | `imagesInformative` 고유 개수 (프록시 URL은 원본 파라미터로 해석) |
| 티 프로필 | 🔴🟡 목록 — **레퍼런스에도 티는 있다. 티 목록이 아니라 위 4개 수치가 목표선이다** |

**섹션 단위** — 같은 스캔에서 해당 섹션의 시그니처(행·열/균일성/정렬/미디어)·밀도·자산을 레퍼런스의 동종 섹션과 대조한다(Land-book 섹션 필터가 동종 표본 수집에 유용).

**컴포넌트 단위** — 페이지 지표는 무의미하다. scan.json의 요소 측정값(크기·패딩·radius·폰트·상태별 스타일)을 디자인 시스템 스펙(위 1군 문서)과 대조한다: 최소 터치 타깃, 상태 커버리지(hover/focus/disabled/loading), 내부 패딩 위계, 토큰 준수. 퀄리티 바의 "디스플레이 모먼트"는 컴포넌트엔 적용하지 않는다.

## 2b. 인터랙션·구조 프로브 (레퍼런스당 1회 — 수치만 재고 끝내면 절반이다)

```
node scripts/probe.mjs --url <레퍼런스> --out _landing/bench/<이름>
```

`interactions.json`이 기록하는 것: **호버 전후 computed diff**(어떤 속성이 얼마나 변하나, 무반응 요소는 몇 개인가) · **스크롤 리빌**(정지 시 숨김 → 등장 요소 수·표본) · **모션 언어**(transition duration·easing·property 분포 — 잘 만든 사이트는 duration이 1~2개 값으로 수렴한다) · 고정 내비 거동 · 미디어 사용.

## 2c. 레퍼런스 분석 문서 → `references/library/<이름>.md` 저장 (신규 분석 시에만)

scan.json(수치) + interactions.json(동작) + crops(구조)를 근거로 문서화해 **라이브러리에 저장**한다. **문서 없는 벤치마크는 벤치마크가 아니다** — borrow.md와 plan.md는 라이브러리 문서를 인용해야 한다.

```
# <레퍼런스> 분석
장르/단위 · 분석일 · 상태(완전|인터랙션 미채움)
## 수치 — 폰트 단수·디스플레이 배율·밀도 중앙값·고유 자산 수·티 프로필
## 구조 — 섹션 순서·역할 (무엇을 어떤 순서로 말하나, 각 섹션의 자산은 무엇인가)
## 자산 운용 — 실스크린샷/사진/일러스트/그래픽을 어디에 어떻게 (고유 수·배치 문법)
## 인터랙션 — 호버 표(요소 유형별 변하는 속성·정도), 스크롤 리빌 패턴, 모션 언어(duration·easing 수렴값)
## 배울 것 — 이식할 구체 항목 (수치·속성 포함)
## 버릴 것 — 이 레퍼런스의 티·반프로필과 충돌하는 것
```

## 3. 갭 표 작성 → direction.md에 첨부

내 대상과 레퍼런스들을 한 표에 놓고, **가장 크게 벌어진 축부터** 재설계 우선순위로 삼는다.
실측 사례(2026-08, 재도장 SaaS 랜딩): 밀도·폰트 단수는 이미 레퍼런스권, 실제 갭은 **자산 다양성(고유 2 vs 16~59)과 디스플레이 배율(3.8x vs 4.1~6.4x)** 둘뿐이었다 — 룰만 봤으면 놓쳤을 결론.

## 4. 경계

- **복제 금지** — 벤치마크는 수치·문법(스케일 감각, 자산 밀도, 섹션 리듬, 컴포넌트 스펙)만 가져온다. 레이아웃·자산을 그대로 베끼는 건 sg-web-replicate의 영역이고 이 스킬에선 위반.
- 레퍼런스의 티(예: 보라 그라데이션)는 목표선이 아니다 — 수치만 배우고 티는 반프로필에 넣는다.
- 벤치마크 실측값이 퀄리티 바 고정값(디스플레이 4배 등)과 다르면 **실측이 우선**한다.
